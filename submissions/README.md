`1.zip` сохраняет исходный `submission.zip` байт в байт. SHA-256 `e99245e771cb78e7a3a2447197843169ac8ee80af57a271aaf149cc1a99be541`.

Баллы и длительности в таблице взяты из истории отправок. На прежнем срезе лидерборда № 1 занимал 78-е место из 92 с баллом 0,116.

На 29 локальных сценариях `2.zip` поднял Recall@10 с 91,4% до 96,3%. Все размеченные фрагменты попали в контекст в 27 из 27 сценариев с источниками против 25 из 27 у `1.zip`. Медиана объёма контекста снизилась с 7546 до 7227 знаков. Это измерения лексического поиска по предоставленной базе.

Из корня репозитория команда `python build_submission.py` создаёт следующий номер. Архивы соответствуют версиям, отправленным или подготовленным к отправке. Результаты новых проверок можно записывать в таблицу рядом с номером архива.

## Сравнение № 2 и № 3

| Локальная проверка | № 2 | № 3 |
| --- | ---: | ---: |
| BM25 Recall@5 / Recall@10 на 29 сценариях | 79,0% / 96,3% | 79,0% / 96,3% |
| Все эталонные фрагменты в контексте генерации | 27/27 | 27/27 |
| Все эталонные фрагменты в запросе верификатора с фиксированными черновиками | 24/27 | 27/27 |
| Медиана объёма JSON для верификатора в той же проверке | 4 105 знаков | 7 962 знака |
| Демо-CSV с правильным порядком ID и непустыми ответами | 18/18 | 18/18 |
| Вызовы тестового шлюза на демо-CSV с одним обрезанным ответом | 18 | 20 |
| Полное время запуска CSV в том же прогоне | 1,25 с | 1,16 с |

№ 3 повторяет оборванный ответ шлюза, даже если полученный JSON синтаксически корректен. В тесте повтор вернул оба пункта договора и потребовал одного дополнительного запроса генерации и одного запроса проверки. Остальные 17 ответов в этом прогоне имитировали недостаток данных для проверки контракта CSV. В обоих архивах прогон использовал Python 3.12 и `rapidfuzz==3.14.1`.

Верификатор получает весь отобранный контекст. В тесте с исключением за пределами первых семи фрагментов это позволило снять неподтверждённый вывод и сохранить подтверждённую часть. Валидный ID с опечаткой в цитате отправляется на проверку с дословным фрагментом. Пустой список выводов при статусе `answered` считается техническим сбоем. В проверке номеров договоров с типографскими дефисами точная привязка сработала в 10 из 13 запросов против 3 из 13 у № 2.

Повторный поиск в целевом сценарии восстановил ответ за три вызова вместо одного. Если новые фрагменты нашлись, но ответ восстановить не удалось, потребовалось два вызова. При отсутствии новых фрагментов хватило одного. При имитации сбоев BGE-M3 и Qwen результат поиска совпал с BM25 во всех 29 сценариях.

Проверили также прямой дословный ответ по одному пункту. Три специально составленных запроса дали тот же факт и цитату с нулём вызовов вместо двух на тестовом шлюзе. Этот вариант остался за пределами выпуска, поскольку не сработал ни на одном из 29 размеченных и 18 демонстрационных вопросов.

В Docker прошли 24 регрессионных теста. Веб-чат в режиме поиска вернул цитаты, исходный документ содержал проверенную цитату, Phoenix принял трассу. Архив содержит шесть файлов в корне, занимает 32 219 байт и даёт тот же CSV, что рабочая версия. SHA-256 `b1e6d550710ba41af2c39006702f4b3fa707e8c613bb9b11a47a8d8aae337ebe`.

Для проверки качества и времени на DeepSeek V4.1 Flash нужны реквизиты реального прокси. Сравнение трёх режимов поиска с BGE-M3 и Qwen3 Reranker 8B и оценка № 3 на закрытом наборе платформы ещё не проводились.
