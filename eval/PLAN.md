# План проверки следующего сабмита ПСБ

Цель — увеличить долю полных и подтверждённых ответов при смене формулировки, даты, контрагента или условия. По регламенту выдуманный факт обнуляет оценку за вопрос. Закрытые вопросы и эталоны платформы недоступны. Локальная проверка моделирует такие изменения на официальной базе.

## Порядок работы

1. **Зафиксировать базу сравнения.** Использовать `submissions/3.zip` и одинаковые входные файлы, настройки поиска, модель и параллелизм. Прогнать текущие сценарии из `eval/cases.json` и новые сочетания условий из `eval/holdout.json`. Для следующих итераций заранее откладывать целые семейства договоров, редакций и связанных вопросов. Все перефразировки и обе стороны контрольной пары держать вместе. Если случай использовали для настройки, добавить его в регрессию и пополнить отложенный набор. Такой принцип применили авторы решения Kaggle U.S. Patent Phrase Matching, группируя примеры по исходной фразе. [Разбор третьего места Kaggle](https://www.kaggle.com/competitions/us-patent-phrase-to-phrase-matching/writeups/s-x-r-d-gsdata-3rd-place-solution), [The Ladder](https://proceedings.mlr.press/v37/blum15.html)
2. **Разметить, что должно меняться в ответе.** При перефразировании сохраняются вывод и источник. При смене даты, договора, порога или условия меняются применимое правило и, где предусмотрено, результат. Отдельно проверить уточнение в последней реплике, условие из ранней реплики, две даты с разными ролями, расчёт с ограничением, ложную предпосылку и отсутствие нужного положения при наличии похожего. Размечать точные фрагменты и ожидаемые связки «договор или редакция, значение, единица, событие, источник». [CheckList](https://aclanthology.org/2020.acl-main.442/), [LegalBench-RAG](https://arxiv.org/abs/2408.10343), [Law-in-Force Retrieval](https://aclanthology.org/2026.aacl-long.42/)
3. **Локализовать ошибку до изменения кода.** Для каждого сбоя проверить фрагменты поиска и их применимость, черновик, решение верификатора и итог в CSV. С той же моделью сравнить обычный контекст с эталонными фрагментами, чтобы отделить ошибку поиска от ошибки применения нормы. Сверять утверждения по отдельности. Наличие всех чисел и ссылок в тексте может скрыть переставленные между договорами сроки. Ошибочные ответы без основания и необоснованные отказы считать отдельно. [Legal RAG Bench](https://arxiv.org/abs/2603.01710), [RAGChecker](https://arxiv.org/abs/2408.08067), [NoMIRACL](https://aclanthology.org/2024.findings-emnlp.730/)
4. **Проверять по одному изменению.** Сначала исправлять воспроизводимые ошибки распознавания договора, переноса условий диалога и определения применимой редакции. Затем сравнить порядок размещения основного пункта и его исключений при одинаковом наборе фрагментов. В измерении на № 3 первые 10 выбранных фрагментов сохранили все основания в 25 из 27 размеченных сценариев. Полный контекст сохранил их в 27 из 27. С доступом к прокси сравнить лексический поиск, добавление BGE-M3 и добавление Qwen на одинаковых входах. Для экономии времени проверить ограниченный дополнительный поиск по недостающему условию. В Kaggle LLM Science Exam искали от статьи к точному фрагменту и запускали более затратные этапы для менее уверенных прогнозов. Для ПСБ переносим этот принцип, измеряя пользу и стоимость дополнительного поиска на тех же вопросах и с той же моделью. [Kaggle LLM Science Exam, седьмое место](https://www.kaggle.com/competitions/kaggle-llm-science-exam/discussion/447155), [Lost in the Middle](https://aclanthology.org/2024.tacl-1.9/), [Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/)
5. **Прогнать путь от входа до ответа.** Проверить распакованный ZIP через `solution.py` с `DATA_DIR`. Сверить CSV с разметкой по сумме, сроку, единице, дате, договору и ссылке. Проверить тот же смысл в веб-чате и открыть дословную цитату в полном документе. Для проверки зависимости от источника прогнать один вопрос на временной копии базы с изменённым числом или сроком, затем с удалённым решающим пунктом. Проверить, что ответ следует за изменением в источнике и сообщает о пробеле после его удаления. Запуск с тестовым шлюзом проверяет поведение кода при заданном ответе API. Качество генерации проверять отдельным запуском с DeepSeek V4.1 Flash.

## Приёмка

- Сравнить версии на одинаковых сценариях по полным подтверждённым ответам, неверным значениям и редакциям, необоснованным отказам и техническим сбоям. В итоговой таблице показывать абсолютные числа по каждому набору. Сохранять изменения, которые исправляют воспроизводимый дефект и проходят исходную регрессию.
- Зафиксировать медиану и p95 по вопросам, вызовы генерации, поиска и реранжирования, восстановленные повторы и полное время формирования CSV. С реальным прокси сверить полный прогон с лимитом платформы в 20 минут.
- Проверить состав ZIP, допустимые версии зависимостей, один непустой ответ на каждый ID и совпадение цитат с источниками. Данные для оценки, эталонные ответы и ключи хранить вне сабмита.

Базовые команды запускаются из корня репозитория. Для проверки архива передать его вместо `.`. При настроенном прокси добавить `--live --audit --json` для разбора выданных ответов и источников.

```sh
python evaluate.py --baseline submissions/3.zip --candidate . --details
python evaluate.py --baseline submissions/3.zip --candidate . --cases eval/holdout.json --details
```
